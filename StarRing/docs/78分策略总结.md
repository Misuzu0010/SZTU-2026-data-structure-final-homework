# 星环算力平台调度：78 分版源码分析

本文讲的是从 68 分版改出来、封存在 `StarRing/baselines/score78/` 的第三版(未上传)。最大的改动是：**估机架工期时，不只数有多少核，还要看已经有多少活排在这里。** 实验取舍见[78 分版迭代记录](78分迭代记录.md)。

## 1. 一轮调度仍分三步

`run()` 的交互顺序和对账没有改。`schedule()` 先估各条流程是否值得继续，`forecast()` 粗排机架并对前四架调用 `plan()`，`place()` 最后核对真实资源和镜像、选机器并发出 `RUN`。三层判断并不重复：分别回答「值不值得做」「放哪里做」和「现在能不能启动」。

与[68 分版](68分策略总结.md)一样，规划沿依赖顺序估算传输、镜像、运行时间和后续费用；只有实际启动才更新真实状态。租户侧的积压仍用于新流程的排序。新增的机架积压则进入 `plan()`，直接影响候选机架的工期和收益，二者不是同一个指标。

## 2. `schedule()`：每个机架还有多少工作没做

每轮清空并重建 `rackDebt` 与 `rackCores`。对已开工、尚有工作且还在收益窗口内的流程，把它的估计剩余核时加到当前锚定机架。估值是「未完成作业的输入估计核时 × 租户时长倍率 + 未完成作业的核数和」，没有逐个扣除已运行的时间。随后把各机架的**在线总核数**加起来，包含已被占用的核，而不是只数眼下空着的核。

## 3. `plan()`：把拥堵折算成等待

原工期取「最长依赖链」和「总工作量摊到机架核数及租户配额」两者中的较大值。78 分版再加上 `0.25 × 其他流程的估计核时 / max(1, 机架在线总核数)`。给已开工流程评估它自己的锚定机架时，先扣掉自身那份工作量，避免自己的活既算成运行时间，又算成排队时间。

比如两架都有 16 核：一架已有 640 核时积压，另一架只有 160 核时。不计自身时，两者分别加 10 和 2.5 个 tick。原本 CPU 单价略低的机架，可能因做完更晚而不再合算。这只是折算，不是模拟真实的先来后到队列。

`place()` 第一次成功启动某条流程时，会把它的工作量立即加到对应机架，避免同一 tick 后面的试算完全看不见新增投入。积压每轮重建；这一版没有在 `forecast()` 改锚点时同步搬账，不能把它当作每次放置后都完全准确的负载表。

## 4. 当前选用的数据结构

| 数据结构名称 | 源码里的实现 | 对应策略 |
| --- | --- | --- |
| 两个定长机架负载数组 | `array<double, 30> rackDebt`、`rackCores` | 直接查机架积压和在线总核数，折算拥堵等待；不维护真实的排队顺序。 |
| 二维动态数组 + 机架下标 | `vector<vector<int>> rackMachines`、`Flow::anchor` | 从首选机架取机器列表，并把已开工流程的估计工作量归到该机架。 |
| 租户索引数组 + 祖先路径数组 | `vector<double> committed`、`Tenant::path` | 保留 68 分版的租户侧等待；它用于新流程排序，不等同于机架拥堵。 |
| 三个并行动态数组 | `vector<double> finish`、`stage`、`charges` | 保留整条流程试算，机架等待叠加在原工期上，不改变作业阶段的真实状态。 |

两张负载表各固定 30 项。每轮扫描流程和机器即可重建；单次规划只需查两次表并做一次等待估算，不必重新遍历其他流程。哈希表、正反邻接表、两级 LRU、网络距离表和告警窗口沿用[68 分版](68分策略总结.md)，仍负责精确状态，不拿拥堵估计来对账。
