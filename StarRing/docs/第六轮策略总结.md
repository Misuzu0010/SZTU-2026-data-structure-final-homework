# 星环算力平台调度：第六版源码分析

这份文档从头讲解[第六版阅读源码](../../StarRing_阅读版.cpp)。程序不只是给作业找一台空机器：它一边维护裁判所见的状态，一边判断整条工作流是否值得开工、放在哪个机架、下一步先跑哪个作业。前者必须按题意算准，后者是在不知道真实时长的情况下做选择。

第一次读代码，可以先跳到 `run()` 看一轮交互，再从 `schedule()` 顺着读 `choose_rack()`、`plan_on_rack()` 和 `place_job()`。碰到网络、镜像或计费时，再回头看对应的数据结构。

## 1. 主循环：先回答问题，再调度

入口是 [`main()` 和 `run()`](../../StarRing_阅读版.cpp#L1706)。`initialize()` 先读机器、网络、租户、镜像和告警规则。之后每个 tick（一个时间步）按下面的顺序处理：

```text
读入 TICK → 清掉过期告警 → 按顺序处理事件
         → 回答 ANS     → 决定 RUN / KILL → 输出 END
```

这里的顺序很重要。比如裁判在这一轮问 `HEAD`，程序要先把已经完成的作业释放掉，但还不能把这一轮准备启动的作业算进去。`answer_queries()` 就放在 `handle_event()` 之后、`schedule()` 之前。`buffered_io` 用 64 KiB 缓冲读入，把整轮回复拼好后一次写出并刷新，避免裁判还在等 `END` 时程序就去读下一轮。

## 2. 工作流怎么存，作业什么时候能跑

看 [`job_state`、`workflow_state` 和 `read_workflow()`](../../StarRing_阅读版.cpp#L423)。裁判给的是外部作业编号，程序用 `job_index_by_id` 查到内部下标。同一条工作流的作业连续放在 `jobs` 里，由 `workflow_state` 的 `[jobs_begin, jobs_end)` 标出；前驱和后继也各放在一个大数组里，每个作业只记自己的那一段。这样扫描整条工作流时不用在许多小容器之间跳来跳去。

每个作业用 `unfinished_predecessors` 记录还有几个前驱没完成。比如 A、B 都是 C 的前驱，C 起初的 `unfinished_predecessors` 是 2；A 完成只会让它减到 1，B 也完成后，C 才进 `ready_jobs`。就绪表和机器的运行表都用「拿最后一项补空位」的方式删除，所以不用移动后面一串元素。

[`release_job()`](../../StarRing_阅读版.cpp#L739) 区分两种退出：收到 `DONE` 就释放资源、记录输出，并通知后继；被故障打断或被程序 `KILL`，则只释放资源并回到待运行状态，不算完成，也不给后继交付数据。机器故障会清空机器缓存；机房停电只改变网络节点状态，机器故障由单独的 `FAIL` 事件处理。

## 3. 对账和启动检查靠哪些状态

### 配额和账单：每次变动，只更新一条路径

`initialize()` 给每个租户预存了到根的路径。[`remaining_quota()` 和 `update_account()`](../../StarRing_阅读版.cpp#L708) 沿这条路径处理资源和费用：作业占用 4 核，就给所属租户和每一级上级各加 4 核。`HEAD` 取各级「配额减已用核数」的最小值。例如自己还剩 8 核、上级只剩 3 核，实际就只能再用 3 核。配额可以改低到当前用量以下，程序保留负的剩余额度，不因此自动杀作业。`QUOTA` 把旧值压栈，`UNDO` 再按反序恢复。

账单不用每轮给所有作业累加。每个租户记 `bill_offset` 和当前每 tick 的费率 `billing_rate`，查询时算 `bill_offset + billing_rate × t`。比如 tick 10 启动一个每 tick 花 3 的作业，代码给 `billing_rate` 加 3、给 `bill_offset` 减 30；到 tick 14，就正好多出 `3 × 14 − 30 = 12`。启动时另把拉取费和传输费直接记进去。作业释放时只停止继续收费，不退已经花掉的钱。账单和实际传输费的乘法使用 `__int128_t`。

### 网络和输入：费用相加，等待取最长的一份

[`network_state::distance()`](../../StarRing_阅读版.cpp#L56) 先查机架之间的距离表，没算过才跑 Dijkstra。一次搜索可以顺便保存同一出发机架到其他机架的距离；链路或机房通电状态改变后，旧距离作废。查距离时不会经过离线节点或断开的链路。

`release_job()` 会把同一来源机架的输出存到同一个 `input_data`，但分别保存**字节总量**和**单份输出最长的发送时间**。例如两份输出分别需要发送 2 和 3 个 tick，同一条路的延时是 4，那么准备要等 `4 + 3 = 7`，不是把两份当一份来等；计费仍按两份的总字节数。即使跨架输入是零字节，也不能跳过可达性检查。

### 镜像：估算不改真缓存

[`layer_cache`、`pull_image_layers()` 和 `preview_image_pull()`](../../StarRing_阅读版.cpp#L105) 实现机器和机架两级缓存。每一层直接用编号查是否在缓存中；两个数组记录每层前后是谁。刚用过的层挪到队尾，容量不够就从队头删掉最久没用的层，不用扫描找淘汰对象。

`pull_image_layers()` 按镜像层的顺序查机器、机架，再到仓库。只有仓库拉取量产生仓库费，机架拉取也要花时间。`preview_image_pull()` 在副本上预演，所以比较一台候选机器不会把它的实际缓存「提前捂热」。选定机器后才对真实缓存调用 `pull_image_layers()`。`CACHE` 和 `RCACHE` 直接读各自的 `used_bytes`。

### 告警和松弛时间：对账值与调度估计分开算

[`log_tracker`](../../StarRing_阅读版.cpp#L185) 先按题面频数建赫夫曼树，再把「当前树节点 + 接下来的一个字节」预先算成查表结果；最后不足 8 位的部分单独解码，不把补零当成日志。解出的字符交给 AC 自动机：可以把它理解为同时检查很多关键词的匹配器，重叠出现也会计分，遇到 `_` 就从头开始。每台机器的分数按 tick 放进循环数组，进入新一轮先扣掉过期的一格。这是 `ALARM` 的值；另记的「最近一次命中高权重模式」只用于调度时估计故障风险。

[`job_slack()`](../../StarRing_阅读版.cpp#L796) 不用调度器预测出来的运行时间，而只用题目给的估计时长 `e`。代码从前往后求每个未完成作业之前的最长等待路径，再用 `整图最长路径 − 作业前面的最长路径 − 从该作业开始的最长路径` 得到松弛时间。后一段在工作流到达时已经倒着算好：未完成作业的后继不可能先于它完成，所以这段仍然有效。同一条工作流的完成数没变，重复查询就不重算。

## 4. `schedule()`：先筛工作流，再给作业排队

[`schedule()`](../../StarRing_阅读版.cpp#L1480) 开头更新每个租户的估时倍率、在线机器、空闲资源和各机架的积压。估时倍率来自已经完成的作业：用「完成时刻减启动时刻再减准备时间」还原实际运行时长，再和题目给的 `e` 比较。某租户样本少时，多参考全场平均；样本多了，就更多相信该租户自己的历史。`estimate_duration()` 对仍在跑的作业保留一定的剩余时间，不会因为它比预测慢就假定它下一刻必定完成。

筛选时，已经没有收益机会的运行作业会被 `KILL`，过期的就绪作业不再进入候选表。暂时配额不足则不等于永久放弃：如果剩下的作业里有一个连当前配额上限都放不下，程序这轮不再给整条流程追加投入，配额恢复后还可以再考虑。单作业流程则可以提前检查：如果连最快的镜像准备都来不及，就不必做后面的规划。

拿到 `choose_rack()` 的工期和费用后，程序用**预计回报减预计费用**作为排序的基础。回报在截止后逐渐下降，超过总时限则为零。`estimate_reward()` 把一个常规工期和一个较快工期按 72% / 28% 混合，这是人为设定的估价办法，不是从日志学出来的概率。

排序还要看紧不紧急、已经做了多少、剩下要占多少核和多久。条件接近时，优先续做已有进展的流程，而不是不断新开项目；同一流程里，后面还有较长一串作业在等的那个，也会往前排一点。新流程可以凭一个较乐观的收益估计进入候选表，但仍须过 `place_job()` 的检查；作业较多的新流程还有额外的费用和工期门槛。

**第六版在这里改了配额等待。** `tenant_workload` 记录各级租户下面已开工流程的大致剩余工作量。旧版只要看到积压就给新流程加一段等待；现在还看剩余配额能不能让它们并行。比如新流程剩余 80 核时、预计做 10 个 tick，平均需要 8 核。租户及各级上级至少都能再用 8 核，就不因配额加等待；实际只能再用 4 核，就只算原等待的一半。这个改动只影响新流程排队，不放宽真实配额检查，也不直接改变前面的机架粗排。

## 5. `choose_rack()` 和 `plan_on_rack()`：为整条流程挑机架

[`choose_rack()`](../../StarRing_阅读版.cpp#L1062) 不会一开始就对每个机架把整条流程走一遍。它先按机房单价、已知跨架输入的传输费、首个未启动作业的镜像准备成本做粗排。对新流程，还给已有许多活的机架加一点成本，但这项加价最多是原粗估的 10%。然后只把前四个机架交给 [`plan_on_rack()`](../../StarRing_阅读版.cpp#L966) 细算。

**第六版也在这里改了镜像估价。** 第五版分别找最低仓库费和最短准备时间，可能拿到两台不同机器的结果。第六版先筛出在线、核数和内存够用的机器，每台只看三个样本层，用「仓库费 + 准备期间占核的费用」做比较；选出一台后，才完整预演镜像拉取。粗估按「机架、镜像」在每个七 tick 区间内复用。因为不同作业可能用同一个镜像但要求的资源不同，新流程进入细算前会再检查选中的机器，不合适就用该机架的代表机做估算。代表机只是一个用于估算的起点，不等于最后会把作业派给它。

`plan_on_rack()` 顺着作业的依赖往后算。它对每个未完成作业估计最早开工时间、准备时间、运行时间和费用。已经在运行的作业按所在机房计剩余运行费；尚未运行的作业按候选机架估价。如果前驱正在别的机架运行，代码还会把它将来产出的数据搬运算进去。为了少遍历重复的依赖，`plan_predecessors` 用位集去掉已经能从其他前驱推出来的等待关系；`running_predecessors` 单独记录哪些原始前驱正在运行，不能因为等待关系被简化，就漏掉这些前驱的输出。

整条流程的工期至少要覆盖两个量：最长的一串相依作业要花多久，以及总核时摊到可用核数上要花多久。`plan_on_rack()` 取两者较大值，再加上机架积压造成的估计等待。`choose_rack()` 以预计回报减费用挑出机架，略微偏向保留原机架，避免估价差不多时反复切换。试算的耗时和费用用两组数组交替保存，最后只给胜出的方案倒着算一遍每个作业后面还要多久。这个首选机架保存在 `preferred_rack`；它是后续作业的优先落点，不是把工作流预先锁在某台机器上。

## 6. `place_job()` 和 `try_reroute()`：真正发出 `RUN`

[`place_job()`](../../StarRing_阅读版.cpp#L1336) 接到的是一个已经就绪的作业。`schedule()` 在调用它前会再查一次租户剩余配额，因为队列前面的作业可能刚用掉一些核。`place_job()` 通常在 `preferred_rack` 内找机器；没选定机架时，可以看全部在线机器。它先看机架能不能接到每份输入，再逐台核对空闲核数和内存。对候选机器用实际缓存预演，准备时间取「传输、拉取」两者较慢的一项，不把两段相加。

机器选择不只比单价：镜像拉取慢可能错过截止时间，近期告警或刚修复的机器也会被加上风险代价。程序还比较这一次的费用和后续预计投入，判断这条流程最后的回报能不能盖住它们。已开工流程的费用容忍度略高；另一条候选流程若也可能复用一层较大的冷镜像，`has_shared_image_layer()` 允许在有限条件下放宽一次新流程的入场判断，每个 tick 最多用一次这种例外。

选定后才真正更新机器和机架缓存、扣核数和内存、记账、移出就绪表，最后写入 `RUN`。这一步会立即反映在本轮后面的调度决定里，不等裁判下一轮再通知。

如果已开工流程卡在原机架，且原机架没有能容纳当前作业的空闲机器，[`try_reroute()`](../../StarRing_阅读版.cpp#L1279) 会估计原地等多久，再比较换到其他机架是否划算。它只改变后续作业的放置位置，不移动已运行的作业。试换后仍发不出 `RUN`，就把原机架、积压和作业估计恢复。每条流程每轮最多尝试一次，每轮最多做八次这类救急重选。

## 7. 为什么不会对每个作业反复算到底

源码里的加速做法，主要是把昂贵的步骤留到真的需要时：

| 位置 | 少做了什么 |
| --- | --- |
| `network_state::distance()` | 同一网络状态下，已有机架距离就不再跑最短路。 |
| `choose_rack()` | 最近七 tick 内、完成数没变且已有首选机架时，复用粗规划；需要重选时也只细算四架。 |
| `plan_on_rack()` / `place_job()` | 缓存已证实能容纳作业的机架；同一 tick 且环境版本没变时可复用完整规划。机器故障会清掉容量缓存。 |
| `schedule()` | 只有这轮涉及就绪或运行作业的流程才进入逐条排名；最大未完成作业核数只在必要时重算。 |
| 候选队列 | 用 `nth_element` 每次挑一批，再只排序这一批。放置失败累计到上限就停止尝试，后续批次也会剔除已明显放不下的作业。 |

这些取舍也有边界。`plan_on_rack()` 的工作数组只给 40 个作业，`schedule()` 明确不接纳超过 40 个作业的整条工作流，但仍会读入和维护其对账状态。四个机架的粗筛、失败次数上限、按历史估时，都可能漏掉更好的安排。程序实现的是**在交互中快速选出一个预计划算的方案**，不是证明找到全局最优。实验数据、样例和版本证据单列在[第六轮迭代记录](第六轮迭代记录.md)。
